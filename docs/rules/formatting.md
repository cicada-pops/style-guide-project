# Оформление текста

Правила этого раздела отвечают на вопрос, как разложить текст по странице: заголовки, абзацы, списки, таблицы, выделение, ссылки и изображения.

## ОТ-1. Стройте понятную иерархию заголовков

- На странице один заголовок первого уровня. Он совпадает с названием страницы в навигации.
- Уровни заголовков не пропускайте: после `##` идёт `###`, а не `####`.
- Глубже третьего уровня не уходите. Если нужен четвёртый, разделите страницу.
- Заголовок говорит, что в разделе: «Запуск проекта в Docker», а не «Setup» или «Разное».

Проверка: markdownlint, правила `MD001`, `MD025`, `MD041`.

## ОТ-2. В абзаце — одна мысль

Абзац раскрывает одну мысль и занимает не больше 5 предложений.
Первое предложение абзаца — главное: по первым предложениям читатель должен понять страницу целиком.

## ОТ-3. Выбирайте вид списка по смыслу

- **Нумерованный список** — для последовательных шагов, порядок которых важен.
- **Маркированный список** — для равнозначных элементов, порядок которых неважен.

В шаге инструкции — одно действие.
Результат действия опишите следующим предложением в том же пункте.

Шаги идут в том порядке, в котором их выполняют.
Если для шага нужна подготовка, опишите её в предыдущем шаге или в разделе «Перед началом», а не в примечании после списка.
Ссылку на адрес давайте не раньше шага, после которого этот адрес начинает работать.

## ОТ-4. Расставляйте знаки препинания в списках

Если пункты продолжают вводную фразу, пишите их со строчной буквы, в конце ставьте «;», после последнего — точку.

```text
Для запуска нужны:
- Docker версии 28 или выше;
- Docker Compose версии 2 или выше.
```

Если пункты — законченные предложения, пишите их с прописной буквы и ставьте точку в конце каждого.

## ОТ-5. Используйте таблицы для однотипных данных

Таблица подходит, когда нужно сравнить несколько объектов по одним и тем же параметрам: переменные окружения, параметры метода API, коды ответов.

- У каждого столбца есть заголовок.
- Пустую ячейку заполняйте тире «—».
- Не используйте таблицу для вёрстки, например чтобы поставить два абзаца рядом.

## ОТ-6. Выделяйте элементы интерфейса полужирным

Названия кнопок, вкладок и полей пишите полужирным и точно так, как в интерфейсе: «Нажмите **Отправить ответ**».
Кавычки вокруг полужирного названия не нужны.

Курсивом выделяйте термин при первом определении: «*Дело* — детективная задача, которую решает игрок».

Не выделяйте полужирным целые предложения ради важности.
Для важного используйте предупреждения (правило ОТ-10).

## ОТ-7. Оформляйте технические элементы как код

Моноширинным шрифтом (`code`) оформляйте:

- команды: `make up`, `pnpm dev`;
- имена файлов и каталогов: `backend/.env`, `docker-compose.yml`;
- переменные окружения: `DJANGO_SECRET_KEY`;
- таблицы и поля базы: `person`, `suspect.status`;
- пути и методы API: `POST /api/cases/{case_id}/execute-sql/`;
- значения параметров и ответов: `"завершено"`, `202`.

Не оформляйте кодом названия продуктов: «Docker», а не `Docker`.

## ОТ-8. Пишите текст ссылки, который объясняет цель

Текст ссылки говорит, куда она ведёт: `Порядок запуска описан в [инструкции по локальному запуску](guides/local-setup.md).`
Не делайте ссылкой слова «здесь», «тут», «по ссылке».

Внутренние ссылки на другие страницы документации делайте относительными путями к файлам `.md`.

## ОТ-9. Добавляйте изображения, только если текста недостаточно

- Скриншот нужен, когда без него сложно найти элемент интерфейса.
- Обрезайте скриншот до нужной области.
- У каждого изображения есть альтернативный текст.
- Храните изображения в `docs/assets/images/`, имена файлов пишите латиницей через дефис: `case-card-locked.png`.

## ОТ-10. Используйте примечания и предупреждения по назначению

| Блок | Когда использовать |
| --- | --- |
| Примечание | Дополнительная информация, без которой можно выполнить задачу |
| Совет | Способ сделать то же самое быстрее или удобнее |
| Внимание | Риск потерять данные, сломать окружение или раскрыть секрет |

- Не прячьте в примечания обязательные шаги — их место в нумерованном списке.
- Не ставьте больше двух блоков подряд.

Синтаксис блоков описан в правиле [MD-1](markdown.md#md-1-учитывайте-где-будет-показан-документ).
