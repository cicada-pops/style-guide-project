# Точечные рекомендации

Здесь собраны правила для ситуаций, которые характерны именно для SQL Hunt.

## ТР-1. Пишите название продукта «SQL Hunt»

Название продукта — «SQL Hunt»: латиницей, с пробелом, без кавычек.
Название не склоняется: «в SQL Hunt», «для SQL Hunt».

`SQLHunt` — это имя репозитория, а `sqlhunt.com` — локальный домен.
Их пишите только как код: `cicada-pops/SQLHunt`.

Проверка: Vale, правило `SQLHunt.ProductName`.

## ТР-2. Давайте команды make, а не docker compose

В проекте есть `Makefile` с короткими командами.
В инструкциях указывайте команду make: `make up`, а не `docker compose --env-file ./backend/.env up --build -d`.

Если команде нужен аргумент, приведите реальный пример и объясните, откуда взять значение:

```bash
make logs backend
```

Имя сервиса берётся из `docker-compose.yml`: `frontend`, `backend`, `celery`, `db1`, `db2`, `broker`, `result`.

## ТР-3. Описывайте переменные окружения таблицей

| Переменная | Обязательная | Описание | Пример |
| --- | --- | --- | --- |
| `DJANGO_SECRET_KEY` | Да | Секретный ключ Django | `<your-secret-key>` |
| `POSTGRES_USER` | Да | Пользователь обеих баз PostgreSQL | `sqlhunt` |

Перечисляйте все переменные, которые читает код, а не только те, что есть в `.env.example`.
Если переменная необязательная, напишите, что перестанет работать без неё.

В примерах секретов используйте заглушки в угловых скобках: `<your-secret-key>`.
Никогда не публикуйте настоящие ключи и пароли, даже тестовые.

## ТР-4. Оформляйте SQL единообразно

- Ключевые слова SQL пишите прописными: `SELECT`, `FROM`, `WHERE`, `JOIN`.
- Имена таблиц и полей — строчными, как в схеме дела.
- Каждую часть запроса начинайте с новой строки.
- Размещайте запрос в блоке с языком `sql`.
- В примерах для игроков не ставьте точку с запятой в конце и не пишите комментарии `--`: редактор SQL Hunt отклоняет такие запросы.

```sql
SELECT p.id, p.name, p.description
FROM person AS p
JOIN suspect AS s ON s.person_id = p.id
WHERE p.description ILIKE '%татуировк%'
```

## ТР-5. Описывайте методы API по шаблону

Каждый метод API описывайте по [шаблону метода API](../doc-templates/api-method.md):

- метод и путь — в заголовке блока кода: `POST /api/cases/{case_id}/execute-sql/`;
- параметры пути — в фигурных скобках;
- пример запроса — командой `curl`, пример ответа — в формате JSON;
- коды ответов — таблицей.

## ТР-6. Пишите сообщения об ошибках, которые помогают

Сообщение отвечает на два вопроса: что случилось и что делать дальше.
Игроку не показывайте текст исключения и технические детали — их место в логах.

<!-- vale off -->

| Неправильно | Правильно |
| --- | --- |
| Поле 'sql' не может быть пустым | Введите SQL-запрос: поле запроса пустое. |
| Ошибка запуска задачи: ConnectionRefusedError… | Не удалось выполнить запрос. Попробуйте ещё раз через минуту. |
| Недостаточно опыта для доступа к делу | Это дело откроется, когда вы наберёте 300 XP. |

<!-- vale on -->

## ТР-7. Отделяйте сюжет дела от задания

Текст дела состоит из двух частей:

1. Сюжет — художественное описание, не больше 5 предложений.
2. Задание — что найти, в каких таблицах искать и в каком формате дать ответ.

Задание пишите нейтрально и однозначно, как инструкцию.
Не используйте символы `•` и табуляцию для списков внутри текста: оформляйте списки так же, как в Markdown.

<!-- vale off -->

| Неправильно | Правильно |
| --- | --- |
| Ответом должно быть ID этого человека. | Ответ — значение поля `id` из таблицы `person`. |

<!-- vale on -->

Полный порядок — в [шаблоне описания дела](../doc-templates/case.md).

## ТР-8. Пишите подсказки к полям базы единообразно

Подсказки `help_text` в моделях Django видны в админке и в схеме дела.
Пишите их с прописной буквы и без точки в конце.

<!-- vale off -->

| Неправильно | Правильно |
| --- | --- |
| дата рождения. | Дата рождения |
| тип преступления, связанного с делом: кража, похищение... | Тип преступления, например «кража» или «похищение» |

<!-- vale on -->

## ТР-9. Пишите сообщения коммитов по Conventional Commits

Формат: `type(scope): description`.
Описание — на английском, в повелительном наклонении, до 50 символов.

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `docs` | Изменения документации |
| `refactor` | Переработка кода без изменения поведения |
| `test` | Тесты |
| `perf` | Ускорение работы |
| `chore` | Сборка, CI, зависимости |

Сейчас в истории SQL Hunt встречаются типы `ref` и `upd`.
Вместо `ref` используйте `refactor`, вместо `upd: readme` — `docs(readme): ...`.
