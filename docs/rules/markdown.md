# Правила работы с Markdown

Вся документация SQL Hunt пишется в Markdown и хранится в Git рядом с кодом.
Правила этого раздела проверяет markdownlint: его настройки лежат в файле `.markdownlint-cli2.yaml`.

## MD-1. Учитывайте, где будет показан документ

| Где показан | Диалект | Документы |
| --- | --- | --- |
| GitHub | GitHub Flavored Markdown | `README.md`, `CONTRIBUTING.md` |
| Сайт документации | Python-Markdown и расширения Material for MkDocs | Всё в каталоге `docs/` |

Синтаксис примечаний отличается:

````markdown
<!-- README на GitHub -->
> [!NOTE]
> Текст примечания.

<!-- Страница на сайте MkDocs -->
!!! note "Примечание"
    Текст примечания.
````

Соответствие блоков: `note` — «Примечание», `tip` — «Совет», `warning` — «Внимание».

## MD-2. Пишите заголовки через решётку

Используйте только заголовки со знаками `#`.
После решёток ставьте пробел, до и после заголовка — пустую строку.

Проверка: markdownlint, правила `MD003`, `MD018`, `MD022`.

## MD-3. Размечайте списки единообразно

- Маркированные списки — дефисом `-`.
- Нумерованные списки — числами по порядку: `1.`, `2.`, `3.`.
- Вложенные элементы — с отступом 4 пробела. Python-Markdown не распознаёт вложенность с отступом 2 пробела.

Проверка: markdownlint, правила `MD004`, `MD007`, `MD029`.

## MD-4. Оформляйте код огороженными блоками с языком

- Используйте только огороженные блоки из трёх обратных апострофов.
- Всегда указывайте язык: `bash`, `python`, `sql`, `json`, `yaml`. Для вывода команды — `text`.
- Команду и её вывод помещайте в разные блоки.
- Не ставьте `$` перед командами: кнопка копирования на сайте скопирует его вместе с командой.

<!-- vale off -->

````markdown
Неправильно:

```
$ make up
```

Правильно:

```bash
make up
```
````

<!-- vale on -->

Проверка: markdownlint, правила `MD040`, `MD046`, `MD048`.

## MD-5. Не используйте HTML

Всё, что нужно документации, есть в Markdown и его расширениях.
HTML-теги ломают единообразие и хуже читаются в исходном файле.
Комментарии `<!-- -->` разрешены.

<!-- vale off -->

| Неправильно | Правильно |
| --- | --- |
| `<p align="center"><img src="demo.gif" width="800"/></p>` | `![Игрок выполняет SQL-запрос и отправляет ответ](demo.gif)` |

<!-- vale on -->

Проверка: markdownlint, правило `MD033`.

## MD-6. Выделяйте текст звёздочками

Полужирный — `**текст**`, курсив — `*текст*`.
Подчёркивания `__` и `_` для выделения не используйте.

Подчёркивания встречаются в именах файлов Python, и без форматирования кода Markdown примет их за выделение.
Например, `__init__.py` без обратных апострофов превратится в полужирное «init.py».

Проверка: markdownlint, правила `MD049`, `MD050`.

## MD-7. Начинайте каждое предложение с новой строки

Одно предложение — одна строка исходного файла.
Markdown склеивает строки одного абзаца, поэтому читатель этого не увидит.
Зато в Git видно, какое предложение изменилось, и ревьюер может прокомментировать конкретную фразу.

Длину строки не ограничиваем: правило `MD013` отключено.

## MD-8. Называйте файлы и оформляйте их единообразно

- Имена файлов — латиницей в нижнем регистре через дефис: `local-setup.md`, `execute-sql.md`.
- Файл начинается с заголовка первого уровня.
- В конце строк нет пробелов, файл заканчивается одной пустой строкой.

Проверка: markdownlint, правила `MD009`, `MD041`, `MD047`.

## MD-9. Не вставляйте голые ссылки

Оборачивайте адреса в текст ссылки: `[репозиторий SQL Hunt](https://github.com/cicada-pops/SQLHunt)`.
Если адрес нужно показать целиком, например `http://localhost:3000`, оформите его как код.

Проверка: markdownlint, правило `MD034`.
