# Руководство по стилю документации SQL Hunt

SQL Hunt — веб-игра, в которой игрок расследует уголовные дела с помощью SQL-запросов.
Игрок изучает материалы дела, пишет запросы к базе с подозреваемыми, уликами и алиби и называет преступника.
За раскрытое дело он получает опыт (XP), который открывает доступ к новым делам.

Это руководство описывает, как писать и оформлять документацию SQL Hunt: README, инструкции, справочник API и тексты дел.

## Зачем нужно руководство

Документацию SQL Hunt пишут разные люди: разработчики бэкенда и фронтенда и авторы дел.
Без общих правил каждый пишет по-своему.
До появления руководства в проекте были такие проблемы:

- название продукта писали по-разному: «SQL Hunt» в интерфейсе и `SQLHunt` в README и письмах;
- README написан на английском, а интерфейс, сообщения API и тексты дел — на русском;
<!-- vale SQLHunt.MixedScript = NO -->
- в одном слове встречались кириллица и латиница: в подсказках к полям базы «ФИO» и «cтатус» набраны с латинскими буквами;
<!-- vale SQLHunt.MixedScript = YES -->
- блоки кода были без указания языка, а имена файлов — без форматирования кода;
- обязательные шаги настройки были спрятаны в примечания.

Руководство решает эти проблемы тремя способами:

1. Фиксирует правила и примеры «правильно / неправильно».
2. Даёт шаблоны для каждого вида документа.
3. Проверяет часть правил автоматически с помощью линтеров в CI.

## Область действия

| Вид документа | Где хранится | Основные читатели |
| --- | --- | --- |
| README репозитория | `README.md`, `backend/README.md` | Разработчики |
| Инструкции | `docs/guides/` | Разработчики, авторы дел |
| Справочник API | `docs/api/` | Фронтенд-разработчики |
| Тексты дел | `backend/core/services/case_loader/cases/` | Игроки |
| Сообщения об ошибках и подсказки | Код бэкенда и фронтенда | Игроки |
| Коммиты и Pull Request | Git, GitHub | Команда |

Руководство не регулирует стиль кода.
Для Python действуют правила Ruff, для TypeScript — правила ESLint из `next lint`.

## Читатели документации

**Игроки** — студенты и начинающие аналитики, которые учат SQL.
Они знают основы `SELECT`, но могут не знать `JOIN` и подзапросы.
Читают с компьютера и с телефона.

**Разработчики** пишут бэкенд на Django и фронтенд на Next.js.
Им нужно быстро развернуть проект и найти нужный метод API.

**Авторы дел** придумывают сюжеты и данные для новых дел.
Они могут не знать, как устроен бэкенд.

## Как пользоваться руководством

1. Выберите шаблон для своего документа в разделе «Шаблоны».
2. Напишите текст по правилам из раздела «Правила».
3. Сверьте термины со [словарём и глоссарием](glossary.md).
4. Запустите линтеры — так вы проверите часть правил автоматически. Команды описаны на странице [«Проверка и линтинг»](linting.md).
5. Откройте Pull Request: ревьюер сверит документ с руководством.

У каждого правила есть код, например `СИ-3` или `ОП-2`.
Ссылайтесь на код в комментариях к ревью: «Нарушено ОП-2, замените кавычки».

| Префикс | Раздел |
| --- | --- |
| СИ | [Стиль изложения](rules/voice.md) |
| ОП | [Орфография и пунктуация](rules/spelling.md) |
| ОТ | [Оформление текста](rules/formatting.md) |
| MD | [Правила работы с Markdown](rules/markdown.md) |
| ТР | [Точечные рекомендации](rules/recommendations.md) |

Правила бывают двух уровней:

- **обязательно** — нарушение блокирует merge;
- **рекомендуется** — отступить можно, если в Pull Request объяснена причина.

Если уровень не указан, правило обязательное.
