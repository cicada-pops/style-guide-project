# Как внести вклад в руководство

Руководство по стилю SQL Hunt развивается по принципу Docs as Code: правила хранятся в Markdown, изменения проходят через Pull Request, ревью и автоматические проверки.
Этот документ описывает, как предложить изменение и довести его до публикации.

## Как предложить изменение

Небольшую правку, например опечатку, можно сделать прямо на сайте: нажмите значок редактирования в правом верхнем углу страницы.
GitHub откроет файл в редакторе и предложит создать Pull Request.

Для остальных изменений:

1. Если изменение спорное, например новое правило или отмена старого, сначала создайте issue и опишите проблему.
2. Создайте ветку от `main`:

    ```bash
    git switch main
    git pull
    git switch -c docs/<тема>
    ```

    Имя ветки — тип и тема латиницей через дефис: `docs/code-examples`, `fix/broken-links`, `chore/update-vale`.

3. Внесите изменения и проверьте их локально (раздел [«Как запустить локальную сборку»](#как-запустить-локальную-сборку)).
4. Сделайте коммит по правилам из раздела [«Требования к коммитам»](#требования-к-коммитам).
5. Отправьте ветку на GitHub и создайте Pull Request в `main`:

    ```bash
    git push -u origin docs/<тема>
    gh pr create --base main
    ```

6. Заполните чек-лист в описании Pull Request.

## Требования к коммитам

Сообщения коммитов пишутся по спецификации [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
type(scope): description
```

- `type` — тип изменения из таблицы ниже.
- `scope` — раздел руководства, необязательно: `rules`, `accessibility`, `templates`, `lint`, `ci`.
- `description` — что сделано, на английском, в повелительном наклонении, со строчной буквы, без точки в конце, до 50 символов.

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `docs` | Новые или изменённые правила, шаблоны, страницы | `docs(rules): add rule for code comments` |
| `fix` | Исправление ошибки: битая ссылка, неверный пример | `fix(glossary): correct PostgreSQL spelling` |
| `feat` | Новая возможность сайта | `feat: add search in russian` |
| `refactor` | Перестановка разделов без изменения правил | `refactor(rules): split formatting page` |
| `chore` | Зависимости, линтеры, CI | `chore(lint): add vale rule for dashes` |
| `test` | Тестовые документы для проверки правил | `test(examples): add how-to example` |
| `perf` | Ускорение сборки | `perf(ci): cache pip dependencies` |

Один коммит — одно логическое изменение.
Если правите замечания из ревью, сделайте отдельный коммит, например `docs(accessibility): address review comments`.

## Процесс ревью

1. После создания Pull Request GitHub Actions запускает проверки: markdownlint, Vale и сборку MkDocs. Pull Request с непройденными проверками не рассматривается.
2. Ревьюер проверяет изменение по чек-листу из описания Pull Request и по правилам руководства.
3. Замечания ревьюер оставляет к конкретным строкам и ссылается на код правила: «Нарушено ОП-2, замените кавычки».
4. Комментарии бывают трёх видов:
    - **замечание** — нужно исправить до merge;
    - **предложение** — автор решает, принять ли его;
    - **вопрос** — автор отвечает в комментарии или уточняет текст.
5. Автор исправляет замечания новым коммитом, отвечает на каждый комментарий и отмечает обсуждение решённым.
6. После одобрения ревьюера автор делает merge в `main` и удаляет ветку.
7. После merge GitHub Actions автоматически собирает сайт и публикует его на GitHub Pages. Проверьте, что изменение появилось на сайте.

## Как запустить локальную сборку

Понадобятся Python 3.9 или выше, Node.js 20 или выше и [Vale](https://vale.sh/docs/install).

1. Создайте виртуальное окружение и установите MkDocs:

    ```bash
    make install
    ```

2. Запустите сайт с автообновлением:

    ```bash
    make serve
    ```

    Сайт откроется по адресу `http://127.0.0.1:8000/style-guide-project/`.

3. Перед коммитом запустите проверки:

    ```bash
    make lint
    make build
    ```

    Команда `make build` собирает сайт в строгом режиме: битая ссылка или страница вне навигации остановят сборку.

## Как добавить новый раздел

1. Создайте файл в каталоге `docs/`. Правила кладите в `docs/rules/`, шаблоны — в `docs/doc-templates/`. Имя файла — латиницей через дефис: `code-comments.md`.
2. Начните файл с заголовка первого уровня. Он должен совпадать с названием страницы в навигации.
3. Если раздел содержит правила, придумайте для него префикс из двух букв, например `КК` для комментариев в коде. Нумеруйте правила по порядку: `КК-1`, `КК-2`.
4. Добавьте страницу в навигацию `mkdocs.yml`:

    ```yaml
    nav:
      - Правила:
          - Комментарии в коде: rules/code-comments.md
    ```

5. Добавьте префикс в таблицу на главной странице `docs/index.md`.
6. Если правило можно проверить автоматически, добавьте правило Vale в `styles/SQLHunt/` или настройку в `.markdownlint-cli2.yaml` и строку в таблицу на странице `docs/linting.md`.
7. Запустите `make lint` и `make build` и создайте Pull Request.
